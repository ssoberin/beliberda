# Robast — демонстрационный пайплайн H123_robust

**Используем robast — проверенный вариант `H123_robust`** для выбора дополнительных
микрокатегорий и локальную Qwen3.5-9B-Q8_0 для черновиков. Это название рабочего
варианта H123, **не** отдельная модель `rubast`, давшая такой же score. Лучший
сабмит был сделан через сайт `15181` с `CLASSIFIER_MODEL_PATH=models/h123`;
без явной настройки код по умолчанию выбирает старую C_syntax, которая в этом
checkout не проходит проверку SHA-256. Поэтому **всегда задавайте H123 явно**.

## Быстрый старт для защиты

- Рабочий сайт: `http://192.168.1.181:15181`. Проверка архива из отдельной
  распакованной копии: `http://192.168.1.181:15182` (backend `18019`).
- Архив с весами и кэшем энкодера: `h123-demo-2026-11-16.tar.zst`;
  подробный запуск на одном Linux-хосте — `START_HERE.md` внутри архива.
  Docker-образы и Python wheelhouse **не входят** в архив, для установки нужна сеть.
- Для CSV бота на работающем хосте: `python scripts/run_submission.py input.csv
  submission.csv --base-url http://127.0.0.1:18009 --deadline 900`. Для
  распакованной копии замените порт на `18019`. Вход содержит `description`,
  опционально `testcase`, `mcId`, `title`.
- Выход строго `testcase,microcats,descriptions`; последние два поля — JSON-массивы
  одинаковой длины и порядка. Нет категорий — `[]` и `[]`. При ошибке генерации
  CLI **не создаёт** выходной файл, а не подставляет пустой ответ.

Классификатор предлагает только дополнительные ID 102–106 и исключает исходный
`mcId`. ID 101 из примера организаторов вручную не добавляем. Private test не
используем для обучения и настройки. 50 разных, но шаблонных синтетических
объявлений обработаны в отдельной копии за 20,92 с; это **не гарантия** времени
для длинного входа организаторов и не полный холодный запуск генератора.

Дальше сохранены архитектура, ограничения и история экспериментов. См. также
[инструкцию CLI и provenance](deploy/demo-provenance.md),

## Как работает классификатор семейства C_syntax (демо: H123_robust)

**Действующий baseline сайта — H123_robust, а не чистая C_syntax и не старый TF-IDF.** Задача —
по `description` и исходному `mcId` предложить дополнительные микрокатегории
102–106, максимум по одному разу, без исходной категории. Пустой список допустим.
Генерация текстов начинается только **после** определения категорий. Заголовок
исходного объявления классификатор не использует.

1. `fixed_chunker.py` разбивает описание на фрагменты: длинные списки и услуги
   в конце не должны теряться. Короткие предложения могут оказаться одним
   чанком; смешение в нём предложения и отказа остаётся источником ошибок.
2. Замороженный `Qwen3-Embedding-0.6B` превращает каждый уникальный фрагмент в
   вектор из 1024 чисел. Это **энкодер для поиска**, не генератор черновиков.
   Для каждой категории есть три query-вектора; по сходству с ними выбираются
   три наиболее подходящих чанка объявления (`Top-3`). Поиск тематической
   близости сам по себе не означает, что услугу выполняет автор **сейчас**.
3. Пять SGD-голов дают первоначальные оценки по категориям. Natasha/Slovnet
   разбирает связи слов: действие, отрицание, чужого исполнителя, изменение
   статуса, ограничения «только под ключ». CatBoost объединяет вероятность
   SGD, сходство и метаданные retrieval, синтаксические признаки в финальную
   вероятность для каждой категории.
4. Порог для каждого из пяти ID в установленном комплекте — **0,5**. Исходный
   `mcId` исключается. H123 дополнительно нормализует текст и удаляет инструкции
   из описания; веса, запросы и исходный код проверяет manifest в `models/h123/`.
   Энкодер Qwen3 загружается отдельно из кэша.
   Загрузка и прогрев — один раз при старте backend, запросы классификации
   проходят через ограниченную очередь с одним inference-потоком.
5. Только после этого отдельная генеративная Qwen создаёт редактируемые
   черновики для выбранных ID. В рабочем промпте ей **запрещено пересматривать
   категории**: если классификатор ошибся, она может написать некорректный
   черновик. Формат JSON проверяется, но смысловая истинность текста не
   гарантируется. При ошибке генерации backend может сохранить `microcats` в ответе,
   но CLI отклоняет неполный пакет и не записывает CSV для бота. Подробнее: [backend](backend/README.md),
   [запуск](PIPELINE_RUN.md), [интеграция](INTEGRATION.md).

**Замечание о воспроизводимости:** сайт `15181` работает из
`test-branch-runtime` (commit `857c6d2`) с локальным `backend/.env`, где задан
`CLASSIFIER_MODEL_PATH=models/h123`. Журнал запуска подтверждает SHA-256 H123
CatBoost `30ca7413…`. Изолированный H123-bundle согласован с текущим кодом.
А вот default `models/c_syntax` имеет старый SHA-256 `syntax_features.py` и
не загружается из этого checkout без восстановления соответствующей ревизии.
**Не отключать проверку хешей и не выдавать C_syntax за конфигурацию сайта.**

**Условия и границы.** Категория может быть предложена только вместе с
комплексным ремонтом — это всё ещё предложение услуги; условие заказа нужно
сохранить в черновике. Архивные работы, услуги бывших сотрудников, работы
чужого подрядчика и нынешний явный отказ — не текущие услуги исполнителя.
Частичный отказ от одной операции не отменяет другую предлагаемую операцию
той же категории.

### Куда развивать архитектуру

- **Данные и проверка:** собрать независимую человеческую разметку актуальных
  услуг и свидетельств (в том числе длинные архивы, противоречия, частичные
  отказы, комплексный ремонт); разделять train, calibration/development и
  новую validation. Старые public/V3 тесты уже просматривались, а Private test
  нельзя использовать для обучения, отбора признаков или настройки порогов.
- **Retrieval:** отдельно измерить покрытие *вручную подтверждённых* цитат
  для Top-1/3/5, затем проверить соседние чанки и удалённые актуальные разделы.
  Изменение количества слотов требует перестройки признаков и обучения голов;
  нельзя просто заменить 3 на 5 в работающей модели. Контекст может повысить
  Recall, но добавить нерелевантные фрагменты и FP.
- **Языковая логика:** проверить корректность признаков по отрицанию, автору
  работ, консультации без исполнения, прошлому времени и области действия
  «остальные/кроме/только». Обучать CatBoost с каждой группой и без неё при
  одинаковом grouped OOF/train, выбирать на calibration и один раз оценивать
  на новой независимой validation. Не убирать признаки только потому, что
  один старый тест улучшился: удаление трёх global-признаков уже добавляло
  **22 FP на public validation**, хотя помогало V3.
- **Проверяющий Qwen — только кандидат на эксперимент:** один структурированный
  вызов для спорных объявлений, по всем ID вместе; отклонять лишь при
  подтверждённом неактуальном статусе, `UNCERTAIN` сохранять. Однако дословная
  цитата **не доказывает**, что отрицание относится именно к этому ID.
  Модуль не включён в рабочий API. Для внедрения нужны измеренный выигрыш
  Precision **без неприемлемой потери Recall**, p50/p95 полной задержки и
  отдельная проверка генерации/экспорта.

### Изолированный опыт с Qwen3.5-9B

[Прототип, авторские данные, решения и полный отчёт](output/qwen-veto-prototype/REPORT.md).
Он получает категории у неизменного работающего H123, извлекает Top-3 с соседями и
удалённые ограничения, затем просит генеративную Qwen за **один запрос**
проверить актуальность всех ID. Возможные статусы: `CURRENT_OFFER`,
`PAST_ONLY`, `CURRENT_REFUSAL`, `THIRD_PARTY`, `UNCERTAIN`. Новые ID запрещены;
veto требует дословную цитату, `UNCERTAIN` сохраняется. Поле условия заказа
формируется экспериментально, но **не передаётся** рабочему генератору.
Локальный сервер подтвердил путь `/models/Qwen3.5-9B-Q8_0.gguf` для alias
`avito-qwen`; он не менялся в ходе опыта.

| Отложенные 11 авторских объявлений | FP | FN | Precision | Recall | micro-F1 |
|---|---:|---:|---:|---:|---:|
| H123_robust (сайт 15181) | 5 | 0 | 0,667 | 1,000 | 0,800 |
| H123 + выборочная проверка | 0 | **1** | 1,000 | **0,900** | 0,947 |

Это **малый авторский holdout**, не независимая человеческая оценка настоящих
объявлений. Фильтр исправил FP длинных архивов, но создал **новый FN**:
в примере с актуальной облицовкой керамогранитом Qwen ошибочно распространила
«остальные работы не выполняем» и на плитку. После фиксации правил отдельная
диагностика `case-004` дала `[102,104,106] → [106]`, но это Private test и не
метрика отбора. Одна цитата для 104 там относилась к архиву и не доказывала
заявленный `CURRENT_REFUSAL`. На вызванных случаях медиана Qwen на holdout
**747 мс** (7 из 11); полная добавочная задержка с повторным получением
эмбеддингов не измерена. **Не внедрять без нового независимого подтверждения.**
## Для презентации: TF-IDF против синтаксического пайплайна

**Задача:** из описания объявления выбрать дополнительные микрокатегории 102–106,
не возвращая исходный `mcId`. Одна запись может содержать несколько услуг.
Классификация и написание текста черновиков — разные этапы. Ниже сравниваются
**классификаторы**, без времени и стоимости генерации черновиков.

### Как устроены подходы

- **TF-IDF + SGD (компактный baseline):** слова, сочетания слов и символьные
  фрагменты превращаются в числовые признаки; пять независимых линейных голов
  оценивают категории. Объявление может получить несколько меток. В
  сопоставимом эксперименте на public train 3398 + V3 clean train 2921
  использовались 18 тыс. словесных и 28 тыс. символьных признаков, порог 0,5
  для каждой категории. Это **не** то же самое, что исторический артефакт
  `/srv/Hakaton/models/baseline/tfidf_baseline.joblib` старого сервиса.
  Скрипт исторического обучения вычисляет покатегорийные пороги для отчёта,
  но сохраняет в joblib пороги 0,5.
- **C_syntax (обычный классификатор этой ветки):** `fixed_chunker.py` делит
  длинное описание на фрагменты → замороженная `Qwen3-Embedding-0.6B` кодирует
  их в векторы → для каждой категории выбираются три наиболее близких фрагмента
  (retrieval) → SGD даёт предварительную вероятность → Natasha/Slovnet разбирает
  отрицания, чужого исполнителя, временные и глобальные ограничения → CatBoost
  объединяет признаки в окончательную вероятность. Исходная категория
  исключается; пороги 0,5. Обучение C_syntax — на тех же 6319 примерах;
  энкодер не дообучался. Комплект `models/c_syntax` проверяется по SHA-256.
- **H123_robust** в `models/h123/` — отдельный экспериментальный комплект
  CatBoost/SGD/векторов с предобработкой. Он **не включается автоматически**:
  без переменной окружения путь `backend` использует `models/c_syntax`,
  но действующий сайт загружает `models/h123` через `backend/.env`.
  Не называем H123 универсальным победителем по одному тесту.

`Qwen3-Embedding-0.6B` здесь **не пишет объявления**. После выбора категорий
отдельная генеративная Qwen через OpenAI-совместимый API создаёт редактируемые
черновики. На текущем локальном сервере alias `avito-qwen` указывает на
`/models/Qwen3.5-9B-Q8_0.gguf` (проверено через `/props` 16.11.2026).
В старой документации встречается 7B — это историческое описание.

### Качество исторической C_syntax: одни входы, разные условия

Числа ниже относятся к исходной C_syntax, **не** к работающему H123 и не к сабмиту на закрытом тесте. Сравнивать их с баллом сайта без отдельного запуска нельзя.


Micro-F1 учитывает все пять меток на всех объявлениях. `Exact match` требует,
чтобы весь набор категорий объявления совпал с разметкой.

| Контрольный набор | Объявлений | TF-IDF + SGD, Micro-F1 | C_syntax, Micro-F1 | Разница C_syntax | TF-IDF → C_syntax, FP/FN |
|---|---:|---:|---:|---:|---:|
| Public validation | 729 | 0,933151 | 0,956124 | +2,297 п.п. | 123/122 → 107/56 |
| Public test (`official_208`) | 208 | **0,824047** | 0,819767 | −0,428 п.п. | 106/14 → 111/13 |
| Сложный синтетический V3 test | 600 | 0,692625 | **0,915916** | +22,329 п.п. | 113/408 → 88/80 |

Таким образом, **на public test превосходство C_syntax не доказано**; сильный
выигрыш наблюдается на сложном V3 с отказами и чужими исполнителями. Public
validation — не закрытый тест. В public test найдены противоречивые ответы для
одинаковых текстов и 20 пересечений с train; V3 создан авторами проекта и не

### Ресурсы: не смешивать разные типы замеров

| Что измерено | TF-IDF + SGD | C_syntax / H123 |
|---|---|---|
| Хранение | 2,768 MiB модель | ~0,5 MiB веса SGD/CatBoost и запросы **плюс** ~1,2 GiB кэш энкодера Qwen3 на диске |
| Классификация на CPU | ~1,20 мс/объявление, **среднее по батчу 728** (только TF-IDF + SGD) | CPU-замер прогретого полного пайплайна: ~283 мс на 97 символах, ~2,14 с на 1039 символах (C_syntax); ~272 мс и ~2,21 с (H123) |
| Отдельный GPU-эксперимент с энкодером | GPU не нужен | Qwen3 на T4: ~85,1 мс/объявление в **другом whole-text эксперименте**; пик VRAM ~6,4 GiB |

**Это не end-to-end сравнение в одинаковом режиме:** TF-IDF измерялся
пакетно на CPU, C_syntax/H123 — по одному запросу на CPU; GPU-число взято
из другой серии с кодированием целого текста, а не полного chunking-пайплайна.
Делить эти числа и объявлять точное «в N раз медленнее» нельзя. На длинных
объявлениях время зависит от количества фрагментов. Natasha + CatBoost поверх
*уже готовых эмбеддингов* добавляли в эксперименте около 17 мс/объявление;
основная тяжесть — энкодер. Малые файлы H123 **не означают** модель в 0,5 MiB:
ему нужен тот же внешний энкодер. Данные:
[батч TF-IDF](output/catboost-optimization/tfidf_inference_benchmark.json),
[CPU-латентность C_syntax/H123](output/final-robustness/final_metrics.json),
[GPU-эксперимент](output/qwen3-embedding-sgd/report.md),
[синтаксический слой](output/syntax-aware-experiment/report.md).

### Сравнение с LLM/API и идея использования Qwen 9B

**Пяти независимых LLM-агентов в одинаковом протоколе мы не измеряли.** Нельзя
приписывать им качество, время или экономию без эксперимента. Если каждому
агенту передавать всё объявление, оплачиваемые входные токены примерно
пятикратны по сравнению с одним таким же вызовом; параллельный запуск
сокращает ожидание, но не сумму токенов. Для цены за N объявлений нужны тарифы
за 1 млн входных/выходных токенов, средние токены одного текста и промпта,
количество вызовов и доля повторов:

`стоимость API = N × число вызовов × (входные токены × тариф_input + выходные токены × тариф_output) / 1 000 000`.

При сравнении с локальным решением учитываются также аренда/амортизация GPU,
электричество, загрузка сервера и генерация черновиков: **классификатор может
быть локальным, но Qwen-генерация всё равно стоит ресурсов**. При известном
тарифе и профиле вызовов можно посчитать точку безубыточности; сейчас числа
экономии нет.

Разумная будущая проверка Qwen 9B — **один арбитр на неоднозначные объявления**,
а не пять агентов на каждый текст: передать исходный текст, `mcId`, кандидатов,
цитаты/фрагменты и оценки модели; попросить структурированный ответ только по
102–106 с обоснованиями и проверять схему, повторы, исключение исходного ID и
отсутствие неподтверждённых услуг. Затем сравнить на независимой ручной
разметке TF-IDF, C_syntax, Qwen-only и каскад по Micro-F1, FP/FN, полному
совпадению, p50/p95 времени и цене. Потребуются промпт, адаптер и тесты;
переобучать 9B для первого эксперимента не обязательно. Уже существующий
генератор можно использовать через API, **но** версия модели и пригодность
его сервера для параллельной классификации требуют проверки. Пока это план,
а не измеренный результат и не включённая функция.

`run.sh` выбирает модель `/srv/Hakaton/models/baseline/tfidf_baseline.joblib`
и Python `/srv/Hakaton/.venv/bin/python`; пути можно переопределить через
`AVITO_MODEL_PATH` и `AVITO_PYTHON`. Он всегда импортирует `app` из Git-репозитория.

```bash
systemctl --user status avito-ml.service
systemctl --user restart avito-ml.service  # после изменения кода/API
curl -sS http://127.0.0.1:8001/health
```

Unit запускается в пользовательской сессии; если нужен запуск до входа пользователя
после перезагрузки, администратор должен отдельно включить linger или настроить

локальные заглушки: его демонстрация не является проверкой ML API.
Qwen ожидается по адресу `http://127.0.0.1:8000`; подробности и ограничения API
описаны в [ml-service/app/README.md](ml-service/app/README.md). Не открывайте
