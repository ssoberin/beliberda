# Контрольная точка: Qwen как бинарный верификатор кандидатов

14 ноября 2026. **Эксперимент, не развёртывание.** Рабочий public-only TF-IDF, веса, пороги 0.5, FastAPI, Docker и данные не менялись. Код — `datasets/verification/{verifier,benchmark}.py`, кэш и полные результаты — `/srv/Hakaton/results/verification_v1/`. Git push не выполнялся.

## Протокол

1. Кандидаты: `full` с сохранённым порогом 0.5; дополнительно максимум по строкам/предложениям с ранее откалиброванными на **public calibration** порогами 102=.84, 103=.82, 104=.78, 105=.90, 106=.68. Исходный `mcId` исключается в обоих случаях.
2. Для каждого кандидата Qwen 2.5 7B `avito-qwen` через локальный vLLM получает **полное объявление**, свой лучший кандидатный фрагмент, предыдущую и следующую смысловые единицы и правило границ категории. Structured JSON: `offered: bool`, `reason: str`, `evidence: str`. Один предложенный вид работ достаточен; отрицание другой операции той же категории не отменяет предложение. Неопределённость означает `false`.
3. Ответ принимается только при валидных типах, непустом объяснении и, для `offered=true`, **точной непустой цитате** из исходного описания (до 500 символов). Отказ/неверная цитата и причина сохраняются; сама дословность цитаты **не подтверждает смысл**.
4. Сначала 11 заранее записанных смысловых пар: первый промпт 8/11, общий принцип «достаточно одной операции в категории» уточнён на этом development-наборе. Финальный `verification-v2` дал **9/11**; он **заморожен до проверки тестов**. Две ошибки: отклонил «мы только кладём плитку» как 103 и «не кладём плитку, но монтируем керамогранит» как 103. Некоторые `reason` неожиданно написаны по-китайски, несмотря на инструкцию русского языка.
5. Затем фиксированные 80 public calibration для диагностики, 160 public validation для оценки, весь Synthetic-300 для стресс-теста и **последним** весь public test (208) для контроля без настройки. Порогов/маршрутизации по этим тестам не меняли. Qwen вызывается только для объединения кандидатов, не для всех 5 категорий каждого объявления. На public test часть одинаковых описаний повторяется; кэш дедуплицирует запросы.

## Сравнение четырёх режимов

**P / R / micro-F1; FP / FN** по категориям 102–106. Пустой ответ учитывается, но в micro-F1 не является отдельной меткой. Для всех четырёх режимов один и тот же набор строк и одинаковое исключение исходного `mcId`.

| Synthetic-300 | .5476 / .1136 / **.1881**; 38/359 | 1.0000 / .1111 / **.2000**; 0/360 | .4467 / .3309 / **.3801**; 166/271 | 1.0000 / .3259 / **.4916**; 0/273 |

На development calibration (80) F1: baseline **.9115**, +Qwen **.6777**, сегменты **.9284**, сегменты+Qwen **.6993**. Уже здесь верификатор был слишком строгим; контрольный тест подтвердил ухудшение. `baseline+Qwen` на public test устранил **78 FP**, но добавил **176 FN**. Комбинация с сегментами устранила 104 FP относительно сегментных кандидатов (133→29), но FN выросли **12→193**. Никакого основания внедрять компонент нет.

\* Public test — данные организаторов, но **не независимый чистый gold**: 13 групп одинаковых текстов имеют конфликтующие метки, и он уже использован в прошлых экспериментах. Synthetic-300 — шаблонный стресс-тест, не прогноз официальной метрики.

| Development 80 | 185 / 206 | 206 | .758 / .856 с |

| Synthetic-300 | 84 / 300 | 300 | .156 / .490 с |
| Public test 208 | 377 / 416 | **216** | .630 / .693 с |

Параллелизм ограничен четырьмя запросами. Логические обращения для одинаковых объявлений повторяются в расчёте режима, но сетевые вызовы дедуплицируются по тексту, категории, фрагменту и версии промпта; число 216 не означает, что сделаны только 216 проверок. Время на объявление — максимум измеренных параллельных HTTP-запросов его кандидатов плюс пакетный TF-IDF; это ориентир, **не p95 сквозной задержки API**. Полные задержки, число пустых ответов, exact match, macro-F1 и все ошибки сохранены в `metrics.json`.

## Какие ошибки исправлены, а какие добавлены

- **Удачные отклонения:** на Synthetic-300 все 166 FP сегментных кандидатов отклонены, и 132 из 134 обнаруженных истинных услуг сохранены (FN 271→273). Отказы и вопрос с «Нет» часто обрабатываются правильно. На public test часть FP тоже исчезает.
- **Главная новая ошибка — чрезмерное отрицание:** в public test из ошибочных решений Qwen для истинных кандидатов **166** — собственное `offered=false` (не сбой HTTP и не только строгая цитата), ещё 8 положительных ответов отклонены из-за неточной цитаты, 7 отрицательных имеют неверно скопированную цитату. Например, «Сантехнические работы, пайка труб» Qwen отклоняет, требуя установки раковин; «Электрика, люстры, розетки, штробы» отвергает как «нет явного предложения», хотя объявление прямо говорит «сделают работы, указанные ниже». «Покраска» в перечне работ ошибочно названа не относящейся к 106. Это нарушение правила одной операции и чувствительность к спискам/длинным текстам.
- **Не все FP относительно public gold семантически ложны:** у public test #28, #32 и других одинаковое описание может иметь пустые и положительные метки. Qwen с точной цитатой «Укладка плитки» остаётся FP относительно **пустой** метки #28. Верификатор не может исправить противоречивый gold.
- **Проверка цитаты не проверяет смысл:** точная подстрока встречается и в отказе/SEO; `evidence` хранится вместе с `reason` и причиной отклонения. Встречались нестрогие цитаты, неожиданный китайский текст объяснений и несколько усечённых/некорректных ответов. Исходные ответы и ошибки для каждой кандидатной пары — в `qwen_cache.jsonl`; разбор неверных решений с текстом и баллами — `*_cases.json`.

## Вывод

При этом маршрутизаторе и промпте Qwen **не улучшает** качество на public validation/test: precision растёт ценой катастрофического падения recall и лишней задержки. Синтетический прирост **не переносится**. Не подключать верификатор к работающему API. Следующий эксперимент имеет смысл только с независимым вручную согласованным набором и отдельным исследованием формата вопроса/границ категории; нельзя дальше подбирать промпт по уже просмотренному public test.
