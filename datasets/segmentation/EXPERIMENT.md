# Контрольная точка: сегментация без переобучения

14 ноября 2026. Проверка гипотезы на **неизменённой работающей** пятиголовой модели `/srv/Hakaton/models/baseline/tfidf_baseline.joblib`. Скрипты `segmentation_benchmark.py` и `dataset_shift.py`; результаты вне Git — `/srv/Hakaton/results/segmentation_v1/{metrics,cases,dataset_shift}.json`. Ни API, ни веса, ни данные, ни Docker не менялись. `public-test-dataset.parquet`, Synthetic-300 и наш длинный test — **только диагностика**, не выбор алгоритма/порогов.

## Метод

- `full`: полный текст, сохранённые пороги 0.5.
- `units`: переносы строк, элементы списков и границы предложений. Короткий ответ «Нет/Не делаем» не отрывается от вопроса или предшествующей услуги. **Это не семантический фильтр:** отрицательная строка может получить высокую оценку.
- `window2`, `window3`: максимум оценок по окнам из двух или трёх соседних единиц. Варианты `full+...` берут максимум с оценкой целого объявления. Никаких маркеров генератора Synthetic-300 и словарей категорий в разбиении нет.
- Сетка порогов `.30... .98` с шагом `.02`, отдельный порог на категорию по максимуму F1 **только на public calibration (728)**. При равенстве выбирается более высокий порог. Public validation (729) — основная проверка. Таблица использует эти пороги; применение старого `0.5` к максимуму показано отдельно как диагностическая ошибка.
- Одинаковая схема ответа, исключение исходного `mcId`, пять целей 102–106 и `micro-F1` для всех методов. Цель 101 для других исходных категорий этой моделью недоступна; длинный test ниже сравнивается по пяти доступным целям.

## Почему порог 0.5 нельзя переносить на максимум

На public validation простые единицы с порогом 0.5 сокращают FN **122→29**, но увеличивают FP **116→312** и снижают F1 **.9349→.9136**. Для плитки (103) на calibration 90-й процентиль максимума на **отрицательных** примерах — **.891** (для полного текста .314); для сантехники (104) 99-й процентиль отрицательных — **.997**. Перекалибровка подняла пороги, например `units`: 102=.84, 103=.82, 104=.78, 105=.90, 106=.68. Они улучшают precision, но сами не делают отрицание семантически понятным.

На Synthetic-300 сырое `units` с 0.5 достигает F1 **.5443**, но создаёт **368 FP** (против 38 у полного текста). Откалиброванное `units`: F1 **.3440**, **139 FP**. Это не надёжное улучшение.

## Конкретные случаи

- **Восстановлено:** Synthetic-300 #102, «Монтируем трубы водоснабжения и канализации, устанавливаем смесители и раковину»: на полном тексте старая модель даёт 104 **.133**, на обычной строке **.870**. Для #163 «Сами разводим электрику...» 105 **.204→.954**. В public test #160 строка про замену проводки поднимает 105 **.422→.980**.
- **Новый FP вопреки сохранённому контексту:** Synthetic-300 #295 «Трубы и сантехнику **не монтируем** ... должен проверить сантехник» даёт 104 **.940** на фрагменте. #21 вопрос «делаете штукатурку, плитку, сантехнику, электрику и покраску? **Нет**» остаётся **одним** фрагментом, но даёт 104 **.913**. На 60 таких пустых примерах полный текст даёт 23 FP, сегменты — **120 FP**. Связь вопроса с ответом в тексте сохранена, однако линейный классификатор не интерпретирует ответ правильно.
- **Чужая работа и отрицание:** в длинном test «Разводку труб и установку сантехники выполняет подрядчик заказчика» даёт ложную 104 **.973**; «Плитку не делаю» и «За сантехнику не берусь, это к другим» тоже дают высокие оценки. Теги и SEO-хвосты встречаются среди новых FP.
- **Контраст на новом синтетическом тесте:** 45 примеров с «заказчик поручает другим» остаются без FP при этом способе разбиения, но это повторяющаяся заготовка и не доказывает способность понимать любые чужие работы.

`cases.json` хранит исходные тексты, правильные метки, оценки полного текста, лучшие фрагменты, 76 восстановленных и 93 новых FP на public validation (для единиц с калиброванными порогами), плюс примеры для стресс-тестов. Часть публичных меток противоречива, поэтому «FP/FN» относительно файла нельзя всегда считать семантической ошибкой; ручной аудит — `../postoyanka/FOLLOWUP_AUDIT.md`.

## Различие корпусов

Ближайший public train в **существующем** word+char TF-IDF пространстве (медианная cosine-схожесть): public validation **.6332**, public test **.3636**, Synthetic-300 **.1874**, новый длинный test **.4441**. При пороге cosine≥.8: 298/729, 31/208, 0/300 и 30/293 соответственно. Точных нормализованных совпадений с public train: 0, 20, 0 и 0. Медианная доля неизвестных словных токенов: .0318, .0524, .1405 и .0777. Это **лексическое**, не семантическое измерение; повторяющиеся тексты public test и близкие шаблоны validation влияют на числа. Оно подтверждает различие окружений, но само по себе не доказывает причинность падения F1.

## Рекомендация

**Не внедрять простой максимум сегментов:** выигрыш recall оплачивается FP, прежде всего на отрицаниях, вопросах с отказом и чужой работе; на публичном test выигрыш не подтверждён. Следующий изолированный эксперимент — проверять **отношение исполнителя к услуге на фрагменте**, например консервативным семантическим валидатором кандидатов, сначала на размеченной вручную development-выборке. При этом не использовать генераторские маркеры или public test для настройки. Если валидатор не поможет, сравнить альтернативную модель на таком же независимом ручном эталоне. Сохранённую baseline пока оставить рабочей.
