# Аудит public-test-dataset.parquet

Серьёзные дефекты эталона подтверждены непосредственно по parquet и текстам. Они мешают интерпретировать F1, однако не объясняют все ошибки классификатора. Данные, gold и модель не изменялись; новых обучений и подбора параметров не было.

## Измеренные факты

| Проверка | Результат |
|---|---:|
| Строк в public test | 208 |
| Уникальных описаний, включая сравнение без нормализации | 139 |
| Лишних повторных строк сверх первого экземпляра | 69 / 208 = 33.2% |
| Строк, входящих в группы повторов | 95 / 208 = 45.7% |
| Групп одинаковых объявлений с конфликтующими gold | 13 |
| Строк в конфликтующих группах | 56 / 208 = 26.9% |
| Пересечений с фактическим public train 3398 | 20 строк, 10 уникальных описаний |
| Пересечений с public calibration 728 | 4 строки, 3 уникальных описания |
| Пересечений с исходным public train 10000 | 24 строки, 13 уникальных описаний |
| Пересечений с public validation 729 / V3 train 2921 | 0 / 0 по точному нормализованному описанию |

| Null, пустых описаний, неизвестных категорий, повторов категории внутри строки | 0 |

Нормализация — casefold и свёртка пробелов. Конфликты не являются артефактом нормализации: при буквальном сравнении **title + description** сохраняются все 13 конфликтных групп и все 56 строк. Уникальных пар title + description — 140. Доля пустых меток сама по себе не доказывает дефект данных; нужны тексты и правила.

В parquet только title, description, categories. Поля source_mcId нет. Значение 101 взято из сопровождающего README; фактическую исходную категорию каждой записи независимо проверить нельзя. Проверки совпадений точные, без утверждения об отсутствии перефразированных пересечений.

## Прямые противоречия

Индексы везде начинаются с нуля. Полные исходные тексты и все 13 групп: [conflicts.json](conflicts.json).

|---|---|---|
| 15 и 29 | Полностью одинаковые title и description: «ЧТО МЫ ДЕЛАЕМ: … Штукатурка, шпаклевка … Покраска, поклейка обоев … разводка электрики и сантехники» | В 15: [102,104,105,106]; в 29: [] |
| 40 и 160 | Полностью одинаковое объявление: «НАШИ УСЛУГИ», штукатурка по маякам, обои и малярка, укладка плитки, замена проводки, разводка труб | В 40: []; в 160: [102,103,104,105,106] |

56 строк в конфликтных группах **не означают 56 заведомо неверных строк**. Это число затронутых записей. Но согласованный детерминированный ответ не способен совпасть со всеми их gold одновременно.

## Семантические проблемы: экспертная проверка

Проверены полные тексты перечисленных примеров, а не только совпадения слов. Это адресная проверка, не случайная выборка и не оценка процента ошибочной разметки во всём тесте.

| Строка | Фрагмент | Gold | Оценка по ТЗ |
|---|---|---|---|
| 40 | «НАШИ УСЛУГИ: … штукатурка стен по маякам … поклейка … обоев … укладка керамогранита … замена проводки … разводка труб» | [] | Пять явно предлагаемых целевых видов работ; пустой ответ противоречит перечислению. Та же запись 160 размечена всеми пятью категориями. |
| 30 | «можем … выполнить плитку, покраску, обои»; далее «облицовка, затирка … монтаж сантехники» | [] | Услуги предложены в текущем описании, вне рассказа о завершённом проекте. Как минимум плитка, сантехника и малярка имеют явную опору. |
| 103 | «В работу входит … замена электрики; … разводка сантехники» | [] | Электрика и сантехника явно входят в предлагаемый ремонт. Отказ от мелких отдельных заказов не отменяет категорий. |

| 116 | «Частная бригада выполняет … Штукатурные и шпаклевочные работы под покраску или обои» | [102] | По справочнику подготовка шпаклёвкой под покраску/обои относится к 106. Метка 106 пропущена. В трёх копиях того же объявления она присутствует. |

Правило из ТЗ: выделять услуги, которые исполнитель предлагает, отличающиеся от исходной категории. Ограничение «нельзя утверждать возможность отдельного заказа» относится к содержанию сгенерированного черновика. Его нельзя превращать в правило «если ремонт только комплексом, gold всегда []». Основание: `mvp/innoglobalhack_avito/innoglobalhack_avito/Innoglobalhack-Avito_2026.md`, разделы «Решение должно» и «Дополнительная задача — генерация текстов», и `microcategories-guide.md`.

README явно предупреждает об автоматической слабой разметке public train. Этот документ **не устанавливает происхождение меток public test**; приписывать его разметку определённой модели без подтверждения нельзя.

## Насколько конфликты мешают метрике

При условии одинакового source_mcId=101 и одинакового ответа для одинакового доступного входа:

- неизбежны минимум **48 ошибок по парам «объявление × категория»**;
- неизбежны минимум **22 несовпадения полного набора категорий**;
- даже оптимистическая таблица ответов с доступом к тестовым gold имеет максимум **Micro-F1=0.924290**, а не 1.0.

Это комбинаторная проверка согласованности, без обучения модели. Для каждого одинакового входа и категории выбирается единый ответ. Если положительная метка встречается k раз среди n копий, включение категории добавляет k TP и n−k FP; общий F1 равен 2TP / (295 + количество предсказанных положительных пар). Максимум по этим вариантам даёт указанную границу; она сохраняется при учёте title. Её нельзя использовать как предсказатель, целевую настройку или оценку достижимого обобщения.

48 неизбежных ошибок **не означают**, что можно вычесть 48 конкретных FP у нашей модели или восстановить её «истинный F1»: метрика нелинейна, а настоящие метки не установлены.

## Почему всё равно остаются ошибки модели

Сохранённая C_syntax: полный test F1=0.819767, FP=111, FN=13. После удаления всех конфликтных групп остаются 152 строки: F1=0.812680, FP=54, FN=11. Удаление конфликтов само по себе не устраняет разрыв и даже немного снижает измеренный F1. Остаток также не является идеально проверенным эталоном.

Пример реального ложного срабатывания модели: строки 2, 5, 39, 48, 95, 157 про подъём, выравнивание деревянного дома и замену венцов. Это не штукатурка; baseline предсказывает 102 при gold=[]. Этот сюжет действительно нужно исправлять. Обратный пример: подавление 106 в строке 30 формально улучшает F1, хотя теряет предложенные покраску и обои.

## Вывод и использование

Public test содержит серьёзные внутренние противоречия, пересечения и примеры пропущенных услуг. Его нельзя считать чистым независимым эталоном или оптимизировать модель только по его цифре. Но низкий F1 нельзя целиком списать на тест: реальные ошибки классификации остаются.

Сохранять официальный результат на всех 208 строках и отдельный фиксированный clean-срез; смысловые исправления/регрессии проверять по тексту. Для выбора модели нужен отдельный вручную проверенный реальный контроль. Сам public test не добавлять в обучение, не менять его gold ради улучшения результата и не использовать для настройки порогов.

Воспроизведение: `python output/public-test-quality-audit/audit.py`; нужны duckdb и исходные локальные файлы. Числа, SHA-256, все определения групп и индексы пересечений — [metrics.json](metrics.json). Сохранённые метрики модели взяты из завершённого `output/catboost-optimization/final_metrics.json`; повторного скоринга или подбора не выполнялось.
