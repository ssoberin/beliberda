# Backend для генерации черновиков через Qwen

FastAPI принимает исходное объявление и выбранные категории, отправляет один
асинхронный запрос к удалённому Qwen и возвращает отдельные черновики в формате
frontend. Qwen должен обслуживаться через OpenAI-совместимый API, например vLLM.
Один только SSH-доступ к компьютеру с весами модели не заменяет запущенный API.

Python 3.11+. Все команды ниже выполняются из корня репозитория.

## Установка и запуск

```bash
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
cp backend/.env.example backend/.env
```

Заполните backend/.env. SSH-подключение и ключи в Git не коммитятся.
Классификация C_syntax включена по умолчанию: Qwen3-Embedding-0.6B → fixed chunker
→ category-aware Top-3 → SGD → Natasha/Slovnet → CatBoost. Комплект `models/c_syntax`
сохранён в ветке и проверяется по SHA-256; флаг выбора классификатора не нужен.
Исходная C_syntax обучена на public3398 + V3clean2921, пороги0.5. Дополнение60
и эксперимент Luna не подставляются автоматически. Для переноса того же комплекта
можно задать CLASSIFIER_MODEL_PATH каталогом, но обычный запуск этого не требует.
Энкодер загружается и прогревается один раз в lifespan при старте FastAPI: используется локальный HuggingFace
кэш, иначе скачивается зафиксированная revision. Генератор Qwen7B на API — отдельная
модель; классификация не вызывает его HTTP-сервер. При неверных весах запуск
прерывается, подмены на TF-IDF нет.

Обычный запуск: `python -m uvicorn backend.app.main:app --port 18001`.
Frontend запускается отдельно, команды в PIPELINE_RUN.md.
Классификация выполняется в одном постоянном inference-потоке, очередь16.
Новые процессы или shell-скрипты на запрос не запускаются.

Для автоматического туннеля достаточно указать:

```dotenv
SSH_TARGET=qwen-server
SSH_REMOTE_HOST=127.0.0.1
SSH_REMOTE_PORT=8000
SSH_LOCAL_PORT=18000
QWEN_MODEL=avito-qwen
```

`qwen-server` — существующий алиас из ~/.ssh/config; можно использовать user@host.
SSH_PORT и SSH_IDENTITY_FILE необязательны: используются настройки OpenSSH и
ssh-agent. При заданном SSH_TARGET адрес Qwen по умолчанию:
http://127.0.0.1:18000/v1. Если переопределяете QWEN_BASE_URL, он должен указывать
на локальный порт туннеля. Имя QWEN_MODEL должно совпадать с ID модели сервера.

Обычное SSH-подключение с ключом должно уже работать, а ключ сервера — быть
проверен и сохранён в known_hosts. Backend запускает ssh без интерактивного
ввода пароля и с проверкой ключа сервера. Пароли через API не передаются.

```bash
backend/.venv/bin/python -m uvicorn backend.app.main:app \
  --host 127.0.0.1 --port 18001 --env-file backend/.env
```

Документация API: http://127.0.0.1:18001/docs.
При автоматическом туннеле используйте один worker: каждый процесс приложения
пытается занять SSH_LOCAL_PORT. Приложение открывает туннель при старте и закрывает
его при остановке. При недоступной сети приложение запускается с /health=200,
но /ready=503. После обрыва SSH и при неудачной начальной попытке backend
переподключается с задержками 1, 2, 4 секунды и далее до 30 секунд между попытками.
До восстановления генерация отвечает 503, не обращаясь к отсутствующему туннелю.
После восстановления сети ручной перезапуск не требуется. Отсутствие программы
ssh остаётся ошибкой запуска. Чужой процесс на локальном порту не завершается.

Логи терминала backend содержат события SSH connected/disconnected/reconnect
и диагностическую причину без паролей и содержимого ключей. В /ready при сбое
SSH возвращаются component=ssh и detail; при недоступном API модели — component=qwen.

При генерации backend пишет в stdout/journald `qwen_start`, `qwen_success` или
`qwen_rejected`/`qwen_failed`: ID запроса, этап, категорию, тип ошибки схемы,
время и статус. **Тексты объявлений, промпты, цитаты, сырой ответ модели и
ключи не логируются.** Для ошибок в JSON-ответе есть `requestId`, а заголовок
`X-Request-ID` присутствует и при успехе; код также добавляется к видимому
сообщению об ошибке. По коду можно найти безопасную диагностическую запись:

```bash
journalctl --user -u avito-pipeline-backend.service -n 100 --no-pager
```

Прежние ошибки восстановить нельзя: сырой ответ Qwen не сохранялся.

### Туннель вручную

В отдельном терминале, подставив своё подключение:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18000:127.0.0.1:8000 user@host
```

В backend/.env:

```dotenv
SSH_TARGET=
QWEN_BASE_URL=http://127.0.0.1:18000/v1
QWEN_MODEL=avito-qwen
```

Такой туннель приложение не создаёт и не закрывает. Без SSH_TARGET и без
QWEN_BASE_URL используется http://127.0.0.1:8000/v1 для прямо доступного API.
При авторизации сервера задайте QWEN_API_KEY отдельно от URL.

## API

### POST /api/categories

```json
{"title":"Ремонт","description":"Укладываю плитку и меняю розетки.","mcId":101}
```

`mcId` — исходная категория 101–106 (если не задан, 101); `title` принимается
для совместимости с формой, **но не используется моделью**. C_syntax анализирует
всю `description` в пределах лимита API100000 символов и исключает
исходную категорию. Ответ: `{"categories":[{"id":103,"name":"Плиточные работы"}]}`
(состав зависит от модели); при отсутствии подходящих категорий — `[]`.
Это автоматический совет, его нужно проверять и при необходимости редактировать.
Маршрут использует локальный embedding-энкодер Qwen0.6B и доступен независимо от
состояния HTTP-сервера Qwen-генератора.

`GET /ready` сообщает `categoryGeneration` отдельно от готовности Qwen.

### POST /api/generate

```json
{
  "title": "Услуги мастера",
  "description": "Укладываем плитку и меняем смесители. Работаем только по записи.",
  "categories": [
    { "id": 103, "name": "Плиточные работы" },
    { "id": 104, "name": "Сантехника" }
  ]
}
```

- description обязателен: 1–100 000 символов после удаления крайних пробелов.
- title необязателен, максимум 100 символов. Не служит источником новых фактов.
- categories: от 1 до 6 разных числовых ID 101–106. name необязателен;
  для промпта используется доверенный серверный справочник.
- Необязательный mcId обозначает исходную категорию как контекст. Он не
  исключает явно выбранную пользователем категорию из генерации.

Ответ:

```json
{
  "drafts": [
    { "categoryId": 103, "title": "Плиточные работы", "description": "Укладываем плитку. Работаем только по записи." },
    { "categoryId": 104, "title": "Замена смесителей", "description": "Меняем смесители. Работаем только по записи." }
  ],
  "warnings": []
}
```

Каждая выбранная категория возвращает самостоятельный черновик с непустыми
title и description. Категории определены до вызова Qwen; генератор их не
переоценивает и не заменяет текст шаблоном из-за недословных цитат. Поле
`warnings` сохранено для совместимости с frontend и в этом режиме пусто.
Порядок черновиков соответствует порядку выбора. Незаконченный или слишком
длинный заголовок backend заменяет законченной частью перед скобкой/кавычкой/
двоеточием, а если её нет — кратким названием выбранной категории. Текст и
остальные черновики не меняются; заголовок не обрывается на 50-м символе.
Неправильный JSON, пустой текст, не тот набор ID или сбой API остаются
технической ошибкой, поскольку такой ответ нельзя корректно показать как набор черновиков.

GET /health — жив ли FastAPI. GET /ready — доступен ли туннель/API и есть ли
указанная модель в GET /v1/models. Проверка готовности не запускает генерацию.

Ошибки возвращаются как `{ "message": "..." }`:

| Статус | Значение |
|---|---|
| 422 | Невалидный ввод, повтор категории или недостаточный контекстный бюджет |
| 502 | Ошибка API Qwen, обрезанный ответ или неверный технический формат |
| 503 | Qwen занят или не готов |
| 504 | Истёк общий срок ожидания генерации |

В запрос передаются сразу все выбранные категории. По умолчанию допускаются
2 одновременных запроса к модели, таймаут — 90 секунд, включая ожидание слота.
Повторные генерации после ошибок автоматически не выполняются.

## Системный промпт и проверки

Промпт находится в app/prompts.py. Он требует отдельный самостоятельный текст
на каждую выбранную категорию, сохранение полезных деталей и условий,
запрет выдуманных конкретных операций, цен, опыта и гарантий. Не обещает отдельный заказ услуги,
доступной только в пакете. Исходное объявление передаётся как данные в JSON.

В requested_categories передаются только серверные id и name: типичные
операции из справочника не подмешиваются в исходные факты. В сообщениях перед
запросом примеры для 0, 1, 2, 3, 4, 5 и 6 категорий: длина drafts равна числу
requested_categories; для нуля — {"drafts": []}. Ещё три пары показывают условие заказа вместе с другой
работой, общие сантехнические/электромонтажные услуги внутри комплексного
ремонта и разделение электрики с покраской. Факты из примеров нельзя
переносить в новое объявление.

Qwen возвращает только categoryId, title и text; никаких supported/evidence.
Backend проверяет **только технический формат**: ровно по одному непустому
черновику на каждый выбранный ID, длину текста и завершённость JSON-ответа.
Некорректный заголовок исправляется только целым словосочетанием или названием
выбранной категории; семантические обещания в тексте backend не оценивает.
Дословность цитат не проверяется; классификация уже выполнена. Требования
относительно выдуманных фактов и отдельного заказа заданы в промпте, но LLM
может ошибиться: исполнитель должен проверить и отредактировать результат.
Backend ничего не публикует.

QWEN_RESPONSE_FORMAT по умолчанию включает json_schema со strict=true:
minItems=maxItems числу выбранных категорий, categoryId ограничен переданными ID,
обязательны categoryId/title/text, запрещены лишние поля, заданы ограничения длины.
Промпт также явно указывает количество и ID для текущего запроса. Backend отдельно
проверяет отсутствие повторов и пропущенных категорий. При нуле категорий Qwen
не вызывается: backend сразу возвращает {"drafts": []}.
Для старых серверов доступны json_object и none; автоматического ослабления
строгой схемы при ошибке сервера нет. Даже в режиме none backend проверяет
JSON ответа. Если ответ обрезается, проверьте QWEN_MAX_TOKENS (по умолчанию 4096)
и контекстное окно модели.
По умолчанию перед генерацией проверяется бюджет всех сообщений, включая примеры.
Для vLLM используются count/max_model_len из /tokenize. Для llama.cpp сообщения
сначала форматируются через /apply-template, затем /tokenize получает content;
размер контекста берётся из /props.default_generation_settings.n_ctx.
Префикс reverse proxy перед /v1 сохраняется для всех этих маршрутов.
Из окна вычитаются вход и запас 256 токенов, оставшийся
бюджет ограничивает max_tokens. Описания до 100 000 символов классифицируются
целиком. Если длинный исходник не помещается в контекст генератора, backend
проходит весь текст окнами с перекрытием и извлекает факты и ограничения заказа.
Qwen выбирает номера исходных фрагментов; номера проверяются, а сам текст
backend берёт из исходника без переписывания моделью. Затем Qwen пишет черновики по
собранным фактам. Простой обрезки первых 12 000 символов нет. Этапы извлечения
логируются как qwen_context_*. Если проверенное извлечение не удалось, ошибка
генерации остаётся видимой; категории классификатора сохраняются отдельно.
Для другого OpenAI-совместимого сервера без /tokenize задайте
QWEN_TOKENIZE_BEFORE_GENERATE=0; тогда лимит нужно учитывать самостоятельно.

## Frontend

Запустить frontend с проксированием:

```bash
cd frontend
npm run dev
```

Frontend по умолчанию проксирует генерацию на http://127.0.0.1:18001.
Для другого адреса задайте API_TARGET при запуске frontend.
Выберите исходную категорию, подберите дополнительные категории с помощью C_syntax
или выберите их вручную и нажмите «Сгенерировать черновики».
POST /api/generate совместим с текущим клиентом. Подбор категорий в задачу этого
сервиса входит: POST /api/categories использует зафиксированную C_syntax. Frontend-сервер
проксирует этот маршрут без локальной заглушки вне деморежима. Frontend показывает warnings, в том числе при
частичном успехе. Статус подключения проверяется через /ready.
Старый контракт ml-service POST /generate не является маршрутом этого backend.

## Тесты

```bash
backend/.venv/bin/python -m pip install -r backend/requirements-dev.txt
backend/.venv/bin/python -B -m pytest -q backend/tests
```

Тесты подменяют HTTP-ответы Qwen и не требуют удалённого сервера. Проверяются
контракт frontend, промпт, категории и условия, ошибки и таймауты API, проверка
ответа, готовность модели и управление процессом SSH. Реальная доступность Qwen,
его поддержка JSON-режима и качество черновиков проверяются после настройки
подключения. Сервис по умолчанию запускается на loopback; авторизация входящих
запросов в этом локальном варианте не реализована.

## Единое создание: JSON / CSV и поток результатов

`POST /api/create` объединяет классификацию и генерацию. Поддерживает один
JSON-объект, JSON-массив, `{"items": [...], "generateText": true}` и сырой CSV
(`Content-Type: text/csv`, UTF-8), обычный текст (`text/plain`).
Браузер отправляет исходные файлы в `multipart/form-data`: поле `file` содержит
JSON/CSV/TXT целиком; альтернативно поле `text` содержит введённый текст без
обработки. Необязательное поле `title` задаёт название для записей без своего title.
Передавать file и text одновременно, повторять поля или загружать несколько файлов
в одном запросе нельзя. Формат файла определяется расширением, вставленного текста
— содержимым. Весь разбор выполняется на backend в рабочем потоке.
Лимиты: 300 объявлений и 5 МБ данных; для multipart дополнительно отведено 64 КБ
на заголовки частей и общее название. Файлы закрываются после разбора.

```bash
curl -N 'http://127.0.0.1:18001/api/create?generateText=true' \
  -H 'Accept: application/x-ndjson' \
  -F 'file=@example-input.csv' -F 'title=Услуги мастера'
```

Каждая запись проходит отдельную классификацию и отдельный вызов Qwen, с теми же
моделями данных, что и обычное описание. Тексты разных записей не объединяются.
У длинных описаний могут быть дополнительные вызовы извлечения фактов.
Для multipart ошибки отдельных записей попадают в соответствующий `item_done`,
остальные продолжают обрабатываться. Ошибки синтаксиса файла, кодировки и лимитов
возвращаются JSON-ошибкой до начала NDJSON-потока. Прямой JSON/CSV API сохранён.
Обязательно `description`; необязательны `mcId` (по умолчанию 101), `title`,
`testcase`, `categories: [{"id": 104}]` (только JSON). CSV поддерживает BOM,
запятую / точку с запятой, кавычки и многострочные поля.

```bash
curl -N http://127.0.0.1:18001/api/create \
  -H 'Content-Type: application/json' -H 'Accept: application/x-ndjson' \
  -d '{"description":"Делаем ремонт квартир и меняем смесители.","mcId":101}'

curl -N 'http://127.0.0.1:18001/api/create?generateText=false' \
  -H 'Content-Type: text/csv' -H 'Accept: application/x-ndjson' \
  --data-binary @example-input.csv
```

В режиме NDJSON каждая строка — отдельное событие: `start`, `categories`,
`drafts` (готовые черновики одной категории), `category_error`, `item_done`,
`done`. Каждые 15 секунд без результатов отправляется `heartbeat`.
`index` — индекс исходного объявления с нуля; `testcase` сохраняется, если задан.
`item_done` содержит полный результат записи, `completed` и `total` — прогресс.
`done.failed` — количество записей с ошибками, включая частичные ошибки категорий.
Ошибки внутри потока передаются событиями: HTTP-статус уже равен 200.
Некорректный ввод отклоняется до начала потока.

Без NDJSON Accept ответ одиночного объекта — `{"drafts":[{"mcId":104,"title":"...","text":"..."}]}`;
пакета — `{"results":[{"index":0,"testcase":"case-001","drafts":[...]}]}`.
Если дополнительных услуг нет, `drafts` пуст. `generateText: false` отключает
Qwen: `title` и `text` равны `null`. Query-параметр `generateText` имеет приоритет
над JSON. Ошибка записи возвращается в `error`, частичные ошибки — в `errors`.

C_syntax выполняется в выделенном `ThreadPoolExecutor`. HTTP-вызовы Qwen-генератора
асинхронны; обычно категории одной записи генерируются пакетно и выдаются
отдельными событиями после ответа Qwen. При технической ошибке пакетного
запроса категории повторяются по одной, чтобы сохранить удачные черновики.
Количество работников пула и число
одновременных запросов ограничены `QWEN_MAX_CONCURRENT_REQUESTS` (по умолчанию 2).
Отмена потока отменяет дочерние asyncio-задачи и ожидающие HTTP-вызовы;
уже выполняющаяся синхронная классификация в потоке может завершиться.
Существующие `/api/categories` и `/api/generate` сохранены для совместимости.

В итогах `/api/create` и `item_done` поле `microcats` содержит все категории
классификатора независимо от успешности генерации. `[]` — завершённая классификация
без дополнительных категорий; `null` — классификация не выполнена или завершилась
ошибкой. Поле `drafts` содержит только успешно созданные черновики. В CSV
`microcats` также сохраняет все найденные категории; `descriptions` выровнен по
этим ID, а отсутствующие тексты обозначены `null`. Ошибки сохраняются в `error`.

Для воспроизводимого сопоставления с отдельной разметкой:

```bash
python backend/scripts/audit_drafts.py --drafts drafts.csv \
  --reference private-test-labeled.csv --input private-test-dataset.csv \
  --output /tmp/draft-audit.json
```

Отчёт различает micro-F1 по меткам, полное совпадение наборов категорий и ошибки
обработки. Эталон не передаётся модели и не используется для обучения.


## Подробное логирование

По умолчанию события пишутся в консоль и `backend/logs/backend.log`. Файл
ротируется после 5 МБ, сохраняются 3 предыдущих файла. Время — Europe/Moscow.
Уровень задаётся `BACKEND_LOG_LEVEL=INFO` / `DEBUG`; путь — `BACKEND_LOG_FILE`.
Пустой `BACKEND_LOG_FILE` отключает запись в файл.

Логи покрывают startup/shutdown, проверку SHA-256, поиск кэша/скачивание,
загрузку и прогрев энкодера, HTTP-запросы от начала до последнего байта,
валидацию JSON/CSV, очередь (ожидание/исполнение/переполнение/отмена), результаты
классификации и вероятности, элементы пакета, fallback генерации, HTTP Qwen,
бюджет токенов, SSH и переподключения. Все события HTTP и inference связаны
серверным `request_id`; клиентский идентификатор не принимается на веру.
При ошибке выводится traceback с причинами и местом сбоя. Локальные переменные,
HTTP-тела модели, тексты объявлений, промпты и заголовки авторизации не дампятся.

В API `message` содержит только сообщение ошибки; `code` и `requestId` находятся
в отдельных полях. Необработанные ошибки возвращают JSON500, ошибки в NDJSON
сохраняют идентификатор запроса и не скрывают уже готовые результаты.

```bash
tail -f backend/logs/backend.log
```

Повторный запуск сначала ищет закреплённую revision в
`models/c_syntax/encoder_cache`, затем в общем HuggingFace-кэше, оба раза с
`local_files_only=True`. При наличии кэша HTTP-проверка метаданных и скачивание
не выполняются. Сеть нужна только если snapshot отсутствует в обоих кэшах.
